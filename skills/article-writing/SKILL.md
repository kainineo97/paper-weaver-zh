# Article Writing Skill

## Overview

这个 skill 用于把观点、笔记、访谈、播客、会议记录、录音转写、资料摘录或用户给出的简述稿，写成一篇可直接继续打磨发布的中文长文。

它不是普通摘要 skill，也不是会议纪要 skill。它的目标是生成“文章成稿”：有标题、有中心判断、有冲突、有论证、有案例、有结尾余味，读起来像一篇完整原创文章，而不是把材料机械整理成条目。

核心写法参考中文公众号和产品/商业观点文章的表达方式，尤其适合写面向公众号、人人都是产品经理等内容平台的长文。写作时要学习判断力、结构和节奏，不复制固定案例、固定行业或固定句式。

关键原则：用户给的大纲、简述稿、笔记或转写材料只是素材和方向，不是正文模板。写作时必须重新组织开场判断、论证顺序、案例位置和过渡逻辑，让文章像一篇完整成稿。

## When to Use

使用此 skill，当用户说：

- “写文章”
- “写公众号文章”
- “写成能发布的文章”
- “整理成一篇文章”
- “把这些材料写成文章”
- “根据这些笔记写一篇文章”
- “按之前的文章风格写”
- “写成人人都是产品经理能看的文章”
- “把录音/访谈/会议/播客内容写成中文长文”
- “帮我把这段简述稿扩成一篇完整文章”

不要使用此 skill，当用户只是要：

- 极短摘要
- 会议纪要
- 课堂笔记
- 资料清洗
- 原文提纲
- 社媒短帖
- 标题党文案
- 学术论文格式
- PRD / 技术文档 / 代码说明

如果用户明确要求“整理笔记”“会议纪要”“资料结构化”，优先使用对应的笔记整理 skill，而不是把它写成文章。

## Output Mode

默认输出 Markdown 正文。

文章结构不默认套“主题一 / 核心观点 / 展开来说 / 原文引用”的整理样稿格式。成稿要像自然文章：标题、二级标题、正文段落、必要引用即可。

除非用户要求，否则不要在开头解释“下面我将”。直接给正文。

### 标题

标题必须带判断和冲突，不要只做中性概括。

完成标准：读者只看标题，就能感受到文章的中心判断、矛盾张力或反直觉点。

标题可以使用以下方向：

- 强判断：指出一个明确结论
- 强冲突：把新旧认知、供需矛盾、角色冲突摆出来
- 反直觉：指出“大家以为的问题”和“真正的问题”不同
- 场景钩子：用具体人群、行业、产品或事件切入

避免标题：

- “关于 XX 的思考”
- “XX 学习笔记”
- “XX 整理”
- “浅谈 XX”
- 只有概括，没有判断的标题

### 开篇

开篇要先抓住核心矛盾或反直觉钩子，不要从时代背景、行业背景慢慢铺陈。

好的开篇通常满足：

1. 先抛出一个判断、冲突或反常识观察。
2. 让读者意识到“这件事和我原来理解的不一样”。
3. 三段内进入文章的中心问题或核心判断。

避免开篇：

- “随着时代的发展……”
- “在当今社会……”
- “最近我看了一个材料……”
- “本文将从以下几个方面……”

完成标准：前三段内必须出现文章的中心问题或核心判断。

### 正文推进

正文围绕下面的链条推进：

```text
中心论点
→ 核心冲突
→ 为什么成立
→ 案例 / 材料支撑
→ 旧认知或旧方案的局限
→ 新判断 / 新机会 / 新启发
```

不要把用户给的大纲按条目顺序机械扩写。可以重排材料，只要不违背原意。

每一节都要回答一个问题：“为什么这个判断成立？”

如果材料里有反驳声音、矛盾信息或不确定点，不要抹掉。可以把它放进正文中段，让文章更可信：先承认复杂性，再给出自己的判断边界。

### 案例和引用

优先使用原文、用户材料或上下文里的具体案例、人物、产品、公司、事件、场景。没有材料支撑时，不要编造具体事实。

引用可以保留，但不必每节固定放引用块。引用要服务于文章判断，而不是为了显得有依据而堆砌。

完成标准：主要判断至少有一个具体材料、案例或原文细节支撑。

### 结尾

结尾不要简单复述全文。要把文章收束到更高层判断，最好落到“为什么这件事在当下变得更重要”。

好的结尾可以：

- 把个案上升到一类问题
- 把产品现象上升到行业变化
- 把工具变化上升到人的选择
- 把商业判断落到用户真实需求
- 把争议收束成一个清晰判断

完成标准：结尾读起来像一个判断的完成，而不是“以上就是我的看法”。

## Writing Workflow

1. 识别中心冲突。
   完成标准：能用一句话说清楚“这篇文章表面讲什么，真正冲突是什么”。

2. 判断材料性质。
   完成标准：分清哪些是核心观点、哪些是案例、哪些只是背景信息、哪些不能直接写入正文。

3. 读取用户指定材料。
   完成标准：如果用户说“工作目录下有文章/材料/素材”，先读取本地材料再写。对 `.rtf/.rtfd/.doc` 等格式，在 macOS 上可用 `textutil -convert txt -stdout <文件路径>` 抽取文本；不要因为二进制读取失败就跳过。

4. 生成标题和开篇。
   完成标准：标题不是中性概括，开篇三段内出现核心判断。

5. 重组正文结构。
   完成标准：不是按材料原顺序平铺，而是按论证需要排列案例、解释、反驳和判断。

6. 写完整成稿。
   完成标准：正文自然连贯，可直接作为公众号文章或产品观点文章初稿阅读。

7. 自检并削掉 AI 味。
   完成标准：删除“首先其次最后”“综上所述”“在当今时代”等模板句；删掉没有信息量的过渡段；避免三句一收的机械节奏。

8. 如用户要求保存成本地文档，先确认写入路径，再写入 `.md` 文件。
   完成标准：文件名简洁可识别；写入后报告绝对路径；如果用户要求紧凑排版，删除空白行，保留非空 Markdown 行。

## Writing Style

- 中文为主。
- 直接进入正文，不要先解释写作计划。
- 段落顶格写，段首不要缩进。
- 段落之间不要额外插入空行；保持紧凑 Markdown 排版。
- 不要一句一段地蹦字，段落长短根据内容自然变化。
- 避免机械的“观点—解释—总结”节奏。
- 少一点报告式、会议纪要式、清单式，多一点真实公众号长文的叙述感。
- 可以下判断，不要只做中性转述。
- 允许反问、转折和停顿，但不要写成短视频口播。
- 不要堆概念；判断要落在具体人、事、产品、行业或场景上。
- 不要过度发挥到脱离原文材料。
- 不要把文章写成 bullet point 大纲，除非用户明确要求。

## Handling Source Material

用户给原文、访谈、播客、会议记录、转写稿时，按以下方式处理：

1. 先找文章真正的问题，而不是先找章节。
   完成标准：能说清“读者为什么要读这篇文章”。

2. 从材料中挑选最有代表性的案例。
   完成标准：至少一个主要判断有具体对象、场景或事件支撑。

3. 把案例抽象成一类问题。
   完成标准：读者能看出“这不只是一个例子，而是一类现象”。

4. 保留材料中的关键表达，但不要堆引用。
   完成标准：引用或转述都服务于判断，不是为了复述原文。

5. 给出新的组织顺序。
   完成标准：文章顺序服从论证，而不是服从原材料顺序。

## Common Pitfalls

1. 把大纲当正文。
   修正：用户给的大纲只是素材和方向，成稿必须重新组织开篇、冲突和论证顺序。

2. 写成整理笔记。
   修正：文章不默认出现“核心观点是”“展开来说”“原文中提到”等固定槽位；这些可以作为内部分析，不要机械输出。

3. 标题太中性。
   修正：标题必须带判断、反差或冲突。

4. 只有观点，没有案例。
   修正：从材料中找具体场景支撑；找不到就保持抽象，不编造事实。

5. 过度套用历史示例。
   修正：示例只学结构，不学行业。实际内容必须来自当前材料。

6. 硬套 B2B、SaaS、AI Agent 等熟悉概念。
   修正：只有原文确实涉及这些主题时才写，否则根据原文主题重构。

7. 文章太碎。
   修正：默认写连贯段落，不要把正文拆成 bullet point。

8. 结尾无力。
   修正：结尾要上升到更高层判断，而不是复述标题。

9. 过度发挥，脱离原文。
   修正：可以提炼判断，但判断必须能从原文论证链条中推出。

10. 输出前解释太多。
    修正：用户要文章时直接给正文；必要说明放到正文之后或单独说明。

## Verification Checklist

完成前检查：

- [ ] 标题有明确判断或冲突，不只是中性概括。
- [ ] 开篇三段内提出核心矛盾或反直觉判断。
- [ ] 正文不是大纲扩写，而是围绕中心论点重新组织材料。
- [ ] 每一部分都有“为什么成立”的论证。
- [ ] 至少一个主要判断有具体案例、材料或原文细节支撑。
- [ ] 没有编造原文不支持的事实。
- [ ] 没有默认套“主题/核心观点/展开来说/原文引用”的整理样稿格式。
- [ ] 语言自然、紧凑、有公众号文章感，少 AI 模板味。
- [ ] 结尾收束到更高层判断。
- [ ] 输出格式符合用户要求；如果用户要求紧凑 Markdown，正文段落之间不额外空行。
